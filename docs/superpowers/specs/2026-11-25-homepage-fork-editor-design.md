# Форк Homepage з вбудованим редактором конфігурації — дизайн

Дата: 2026-11-25. Статус: чернетка, чекає схвалення.

## Навіщо

Автору подобаються ідеї двох проєктів, але не їхня реалізація:

- **gethomepage/homepage** (GPL-3.0, Next.js, pnpm) — дашборд. Автору бракує функціональності наявних віджетів (деталі — див. «Відкриті питання»).
- **jchisholm59/homepage-editor** (MIT, Express + ванільний JS, ~1900 рядків) — веб-редактор YAML-конфігу Homepage. Автор повідомив, що вкладка Settings у ньому «нічого не робить».

Мета: **один інструмент** — Homepage з редактором усередині, для особистого використання, з подальшою **публічною публікацією** результату.

## Цілі

1. Один репозиторій, один Docker-образ: дашборд і редактор за адресою `/editor`.
2. Редактор використовує ту саму конфігурацію й версію віджетів, що й дашборд, без окремого контейнера та без ручного оновлення каталогу.
3. Виправити поломку вкладки Settings та пов'язані дефекти каталогу.
4. Розширити функціональність наявних віджетів (етап 3, після уточнення від автора).
5. Публічний форк з чесною атрибуцією та ліцензіями.

## Не цілі

- Не переписувати рендеринг дашборда й формат конфігурації. Існуючі `config/*.yaml` мають працювати без змін.
- Не надсилати PR в апстрім (див. обмеження).
- Не робити з редактора окремий розвиваний продукт.
- Не підтримувати багатокористувацький режим чи ролі.

## Анти-цілі (провал, навіть якщо технічно працює)

- Форк, який неможливо підтягувати з апстріму: правки в ядрі Homepage мають бути мінімальні, увесь код редактора лежить в окремих каталогах.
- Редактор, доступний без захисту, коли він може переписати дашборд.
- Форк, що видається за офіційний Homepage.

## Обмеження

- **Ліцензії.** Результат поширюється під GPL-3.0. Код редактора (MIT) зберігає копірайт автора в `NOTICE`/заголовках файлів.
- **Апстрім забороняє PR, створені переважно ШІ** (`AGENTS.md` у gethomepage/homepage). Тому це незалежний форк. У README вказується, що частину коду створено за допомогою ШІ.
- **Назва.** Не «Homepage» і не така, що видає форк за офіційний продукт. Робоча назва — на розсуд автора (відкрите питання).
- Redirect/rewrite у Next.js і стандарти проєкту: `pnpm lint`, `pnpm test` (Vitest), pre-commit.

## Підходи (розглянуто)

|       | Підхід                                                   | Плюси                                                          | Мінуси                                        |
| ----- | -------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------- |
| **A** | Один форк Homepage, код редактора всередині (**обрано**) | Один інструмент, один образ, один README; мінімум чужих правок | Треба стежити за апстрімом                    |
| B     | Форк Homepage + редактор як git submodule                | Редактор оновлюється окремо                                    | Незручно для клонувальників, фактично склейка |
| C     | Два форки + репозиторій з `compose.yaml`                 | Найпростіше                                                    | Не «один інструмент»                          |

Усередині A розглядалися два шляхи запуску редактора: окремий процес за проксі (швидше, але два процеси й дві залежності) і **нативні Next API routes** (**обрано**). Бекенд редактора — лише ~280 рядків, тож нативний шлях недорогий і прибирає каталог, що застарівав, та HTTP-виклик `revalidate`. Це мій вибір, не обговорювався з автором.

## Архітектура

- Форк `gethomepage/homepage`; віддалений репозиторій `upstream` для регулярних merge.
- **Бекенд редактора** → Next API routes у `src/pages/api/editor/*` (файли, preview/save з YAML Document API, бекапи, іконки, перевірка посилань, каталог). Логіка `lib/sync.js` переноситься як є.
- **Фронтенд редактора** → статичні файли в `public/editor/` (ванільний JS, ES-модулі), сторінка за `/editor` (rewrite у `next.config.js`). Сторонні бібліотеки (`sortablejs`, `marked`, `yaml`, `diff`) стають залежностями Homepage; копіюються в `public/editor/vendor` скриптом на етапі збірки. Деталі розташування — на розсуд виконавця.
- **Каталог віджетів** генерується на етапі збірки з **коду та документації самого форку** (`src/widgets/*`, `docs/`), а не зберігається як статичний JSON. Приклади YAML, які не парсяться (наприклад, із заглушками `...`), або очищуються, або позначаються як «лише довідка» (кнопка «Use this» прихована з поясненням).
- **Доступ.** Редактор **вимкнений за замовчуванням**. Вмикається змінною середовища; при ввімкненні вимагає пароль (як `EDITOR_PASSWORD` в оригіналі), якщо пароль явно не вимкнено. Це мій вибір.
- **Іконки/фони.** Нове в `config/icons` та фонах, як і раніше, підхоплюється Homepage після перезапуску; поведінку перевірити й задокументувати. Кнопку перезапуску через Docker proxy залишити опційною.

## Виправлення, відомі вже зараз

1. **Settings**: у `public/views.js` бічне меню викликає `select(s)` із сирою секцією каталогу, де немає `page`; `store.catalog.configs[s.page].doc` падає з `TypeError` (підтверджено стеком від автора). Виправлення: передавати `{...s, page}`.
2. **Каталог**: приклади з `...` у YAML (`tabs`, `category-icons`, `link-target`, `status-style`, `use-equal-height-cards`, `show-container-stats`, `hide-widget-error-messages` та ін.) не парсяться, тож «Use this» показує оманливе «This example is not a settings block».
3. **Приклади-списки** (`services`, `bookmarks`, `docker`) не можна вставити через «Use this»; інтерфейс має це пояснювати.
4. **Тести**: у редактора немає тестів фронтенду. Додати щонайменше смоук-тест вкладок (кожна відкривається без помилок консолі) і тест, що кожен приклад каталогу або парситься, або позначений як довідка.

## Етапи

0. Форк, `upstream`, нова назва, `NOTICE`, README з розкриттям використання ШІ.
1. Перенос бекенду й фронтенду редактора, виправлення Settings, ввімкнення за env.
2. Генерація каталогу з коду форку, очищення прикладів, тести з п. 4.
3. Покращення віджетів — **обсяг буде визначено після відповіді автора** (див. нижче).
4. Публікація: Docker-образ (ghcr), README зі скріншотами, інструкція оновлення з апстріму.

## Відкриті питання (відповідає автор)

1. **Які саме віджети й чого в них бракує?** Приклади: «віджет X не показує Y». Без цього етап 3 неможливо оцінити. Підказка: у Homepage вже є універсальний `customapi`; частину потреб можна закрити формами в редакторі для нього, решта — нові/розширені віджети в `src/widgets/<name>/`.
2. **Назва** форку.
3. Чи повідомити автора редактора (чемність; ліцензія MIT цього не вимагає).

## Що лишається виконавцю

Точне розташування файлів фронтенду, спосіб копіювання vendor-бібліотек, формат генерації каталогу, налаштування ввімкнення редактора й структура тестів — на розсуд виконавця в межах цілей і обмежень вище.
